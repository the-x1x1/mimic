# Migration audit — photography editor → personal communication model

Written before any code was deleted, renamed or added. Everything below describes the repository as it stood at `v0.5.0-alpha.1`, and assigns every component to **KEEP**, **REFACTOR**, **ARCHIVE** or **DELETE**.

The product is changing from:

> Mimic learns how a photographer edits in Lightroom Classic and reproduces those edits on new shoots.

to:

> Mimic learns how a person communicates and helps them draft responses that sound like themselves.

The two products share almost nothing at the domain level and a surprising amount at the infrastructure level. That asymmetry is the whole point of this audit: the parts of the repository that are worth five releases of hardening are the parts that never knew they were about photographs.

## 1. How this audit was produced

Inspected directly, in this order: `git status`, `git branch -vv`, `git log`, `origin/main` vs `work/next`; the full directory tree; `package.json` (root, desktop, contracts, ui, test-fixtures), `Cargo.toml` (workspace and `mimic-core`), `engine/pyproject.toml`; `tauri.conf.json`; every file under `crates/mimic-core/src` by line count and the eight largest by content; the Tauri command modules; the React source tree; the Python engine source tree; all four SQL migrations and the migration registry; `.github/workflows/{ci,release,nightly-smoke}.yml`; `scripts/`; the fixture tree with sizes; every file under `docs/`; `README.md`; `CHANGELOG.md`; `CLAUDE.md`.

No file was modified during the audit.

## 3. Current architecture, layer by layer

**Desktop shell.** Tauri 2, crate `mimic-desktop`, identifier `com.formicaria.mimic`, single window, dark theme, CSP locked down, asset protocol scoped to the app data directory. Plugins: dialog, opener, process, updater. `startup.rs` resolves `AppPaths`, opens the database, starts the engine sidecar and the bridge, spawns the job runner, and installs the Lightroom plugin copy. Commands are grouped in nine modules (`app`, `diagnostics`, `jobs`, `libraries`, `lightroom`, `sessions`, `settings`, `styles`, `updater`) and every one returns a serde-camelCase payload that the frontend re-validates.

**Native core (`mimic-core`).**

- `db` — one `rusqlite` connection behind a mutex, WAL, `foreign_keys = ON`, `busy_timeout`, forward-only numbered migrations embedded with `include_str!`, timestamped backup written before migrating an existing install, `table_counts()` for diagnostics, online `backup_to()`. Repository modules per aggregate (`repo_assets`, `repo_jobs`, `repo_libraries`, `repo_lightroom`, `repo_sessions`, `repo_snapshots`, `repo_styles`).
- `jobs` — the persistent queue. `JobRunner` drains one job at a time, heart-beats every 3s, honours cancellation between work items, converts stale `running` rows to `interrupted` on startup and re-queues only kinds that declare themselves resumable. `JobExecutor` trait + `CompositeExecutor` dispatch by kind. `forward_engine_progress` pipes sidecar progress events into the job record.
- `engine` — NDJSON-over-stdio client for the Python sidecar: request/response correlation by `requestId`, 32 MiB line cap, timeouts, restart budget, broadcast of engine events.
- `bridge` — axum server bound to `127.0.0.1`, per-launch bearer token, body size caps, long-poll command channel, discovery file written 0600.
- `edit_dna` — normalization of Lightroom develop settings against `edit_mapping_v1.json` (104 controls, 11 families), preservation of unknown keys, `to_lightroom_settings`, `verify_readback`.
- `capability` — runtime probe of what the installed Lightroom can actually write, producing a `CapabilityMatrix`.
- `ingest`, `training`, `sessions`, `corrections` — the four domain pipelines.
- `paths`, `ids`, `version`, `diagnostics` — small support modules.

**Python engine.** A `Server` (NDJSON dispatch, progress events, error envelopes, no shell, no eval) and an `EngineService` method registry binding `engine.hello/configure/health/shutdown`, `scan.folder`, `xmp.parse`, `image.metadata`, `image.analyze`, `image.analyze_batch`, `training.train`, `model.predict`, `session.group`. Underneath: scanner, XMP parser, RAW preview and metadata, statistical features, scene heuristics, a `stats_v1` embedding fallback, a session-grouped train/validation/holdout splitter, baselines, a hybrid KNN+ridge trainer, a confidence scorer, and session grouping/consistency.

**Lightroom plugin.** 16 Lua files implementing handshake, long-poll command loop, capability probe, develop read/write, snapshots, metadata and menus.

**Frontend.** React 19 + Vite 7 + TanStack Query + zod + Radix + zustand. `lib/ipc.ts` validates every command result through a zod schema and throws `IpcError(code, message)` naming the offending path. Pages: Home, Styles (list/detail/new/add-data), Sessions (list/detail/new/confirm-apply), Review, Settings, plus an onboarding flow. `packages/ui` holds design tokens and eight primitives.

**Contracts.** `packages/contracts` mirrors every IPC payload in zod, with checked-in fixtures under `fixtures/` parsed by both the Rust tests and `packages/contracts/test/contracts.test.ts`. This cross-language fixture discipline is the single most valuable practice in the repository: it is what caught the `rename_all_fields` serde bug in slice 5.

**CI and release.** `ci.yml` runs five jobs (frontend, rust, python, plugin, security). `release.yml` verifies that the tag equals the package version and that `sync-version.mjs --check` passes, refuses a dev pubkey for a non-alpha tag, then builds on Windows and drafts a release with `latest.json`. `nightly-smoke.yml` runs a scheduled smoke pass.

## 5. Data model impact

Of the 22 tables at schema v4, five survive and seventeen go.

**Survive:** `app_settings`, `jobs`, `events`, `update_state`, `schema_migrations`.

**Deleted:** `libraries`, `assets`, `sidecars`, `edit_snapshots`, `visual_features`, `style_profiles`, `style_profile_libraries`, `sessions`, `session_assets`, `scene_clusters`, `training_sets`, `model_versions`, `model_artifacts`, `predictions`, `apply_batches`, `applied_edits`, `corrections`, `correction_syncs`, `lightroom_connections`.

The new communication schema arrives as migration `0005`. Because migration `0001` may never be edited, `0005` drops the photography tables explicitly and creates the new ones; a v4 database on a user's disk migrates cleanly to v5 and loses its photography data, which is correct — that data describes a product that no longer exists. The pre-migration backup written by `Db::open` means the old database is still recoverable from `data/backups/` if anyone ever needs it. The migration test is extended so that a seeded v1 database still upgrades all the way to v5.

The new tables, named here so the architecture document can elaborate: `user_identities` and `user_identifiers`; `sources`; `participants` and `participant_identifiers`; `conversations` and `conversation_participants`; `messages`; `message_embeddings`; `voice_profiles` (layered: global, channel, relationship, situational); `representative_examples`; `drafts` and `draft_feedback`; `analysis_runs`.

Two schema-level requirements that the photography schema did not have, and that must be designed in from `0005` rather than bolted on:

1. **Cascading deletion that is real.** Deleting a participant must remove their conversations, those conversations' messages, those messages' embeddings, the representative examples drawn from them, the relationship profile, cached analysis and derived metrics, and must then rebuild the global and channel profiles that were computed over the deleted material. Foreign keys with `ON DELETE CASCADE` handle the first half; the rebuild is an explicit job and is tested.
2. **Scale.** The photography schema was designed for tens of thousands of rows. The communication schema must behave at 100k–1M+ messages: indexes on `(conversation_id, sent_at)`, `(participant_id, sent_at)`, `(direction, channel)`, embeddings stored out of the row, import streamed in batches with progress and cancellation, and analysis run as background jobs over cursors rather than `SELECT *`.

## 6. Dependency impact

**Removed (Rust):** `axum`, `tower`, `tower-http`, `reqwest` (dev). **Retained:** `rusqlite`, `serde`, `serde_json`, `uuid`, `chrono`, `tokio`, `tracing`, `thiserror`, `anyhow`, `rand`, `sha2`, `hex`, `tempfile`.

**Removed (Python):** `pillow`, `exifread`, `rawpy`. **Retained:** `numpy`, `pydantic`, `scikit-learn`, `joblib`, `onnxruntime` (optional).

**Removed (TS):** nothing required. The Radix, TanStack Query, zod, zustand and lucide dependencies all carry over.

**Added:** a model-provider layer. V1 targets a local provider and at least one hosted provider behind one `ModelProvider` trait, with credentials in the OS secure store rather than the database, and no message content in logs by default.

## 7. Risks and sequencing

The largest risk in a migration this size is a half-deleted repository that no longer builds and no longer describes anything. The ordering that avoids it:

1. Land the audit (this file) on its own, so the categorization is reviewable before anything is destroyed.
2. Archive first, delete second, in one commit per direction, so the archive is never reconstructed from a deletion.
3. Add migration `0005` and the new Rust modules while the old ones are already gone, so the crate is never simultaneously carrying two domains.
4. Rewrite contracts and UI against the new commands, keeping `lib/ipc.ts` untouched, so the validation boundary never lapses.
5. Keep `scripts/validate.ps1 -Full` green at every commit. A commit that cannot pass it is not a slice.

Two risks worth naming separately. First, the temptation to keep photography code "just in case" — the answer is that git history and `archive/` already are the just-in-case, and a dead module in the build is a permanent tax on every future change. Second, the temptation to report a "Mimic Score" before the held-out evaluation exists. The old product earned its numbers by measuring them; the new one starts with no numbers and must say so in the UI until the evaluation harness produces real ones.

## 8. What this migration explicitly does not do

No fine-tuning. No autonomous sending. No cloud storage of message content. No "Trusted Mode" implementation, though the three autonomy modes are designed so the schema does not have to change later. No invented metrics — every percentage shown to the user is traceable to a computation documented in `docs/VOICE_ENGINE.md`.
